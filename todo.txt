Still open
----------
None of these is a silent wrong answer except where marked.  Each was
reproduced by the verification pass; repros are in the mbasic write-up.

  - printf field width and the '-', '+' and ' ' flags do nothing on a float
    conversion.  This is not float-specific: the format parser skips '-',
    '+' and ' ' outright for every conversion, so they have never been
    implemented at all.  %10.2f prints "1.50", not "      1.50".  Adding
    them is a feature rather than a fix, which is why it was not rushed in
    alongside the corrections above.

  - %.*f and %*f are unsupported: the specification is echoed verbatim, the
    int argument is not consumed, and every later conversion in that call
    reads the wrong argument.  SILENT.  The compile-time diagnostic does not
    catch it either, because _extract_printf_specifiers swallows the '*'.

  - %lf, %le and %lg are not registered by auto-detection or by
    --printf float, because _extract_printf_specifiers never adds the 'long'
    feature for a float conversion.  SILENT.  mbasic's generated C emits %lg.

  - _auto_detect_printf_features does not descend into a `default:` label or
    an initializer list, so a printf there is invisible to it.  SILENT.

  - A struct return larger than 256 bytes overflows __sret_buf.  The buffer
    is DS 256 and nothing checks the returned type against it: returning a
    402-byte struct emits `ld BC,402` / `ldir` straight into it, writing 146
    bytes past the end over whatever storage follows.  SILENT -- the value
    still reads back correctly, because nothing has used the clobbered bytes
    yet -- and it scales with the struct, so a big enough one reaches
    anything.  Either bound the copy with a diagnostic or return via a
    caller-supplied hidden pointer, which is what the size argues for.
    (The duplicate __sret_buf definition that used to be recorded here is
    fixed: it now has its own runtime.lib module, rt_sret.mac.)

  - _merge_array_size compares only the outermost element count.  Inner
    dimensions, element types and declarator shape are never checked, so
    incompatible redeclarations gcc rejects are accepted and the object size
    depends on declaration order.  SILENT.

  - A negative or zero array size is accepted; a floating-point one is not
    diagnosed by uc80 and surfaces as a um80 parse error with no source line.

  - Compound assignment to a 32-bit, 64-bit or float array element evaluates
    the subscript twice, so a side-effecting subscript runs twice.  SILENT.
    ada0e32's test covers only a 16-bit array.

  - uc80 --build-libs ignores UC80_LIB_DIR for its destination while
    --print-lib-dir reports the override, so `uc80 --build-libs &&
    LIB=$(uc80 --print-lib-dir)` links against libraries that were never
    rebuilt.  SILENT.  lib_dir() also does not make a relative UC80_LIB_DIR
    absolute, so the CLI and the Python API can disagree by cwd.

  - Extended asm and asm goto are not diagnosed when the enclosing function
    is eliminated as dead; the check lives in gen_asm, which never runs for
    code that is not generated.  The AST optimizer also deletes an asm block
    that is unreachable or in a constant-false branch, which matches gcc -O0
    but contradicts the README's "the optimizers do not change, move or
    delete it".

  - _format_asm_block's indentation heuristic rewrites a colon-less MACRO-80
    label whose name happens to be a mnemonic or directive (SET, END, IN,
    OUT, AND, OR, SUB, CP, RES, PAGE, NAME), which the README's "goes into
    the output assembly unchanged" does not allow for.

  - The CR-suppression state tracks only bytes written through __conout, so
    a console write that bypasses it - inline asm today, and BDOS-1 input
    echo on real hardware - leaves it stale and the next '\n' loses its CR.

  - --no-crlf is silently ignored on a translation unit that does not define
    main(), with no warning.

  - No diagnostic for comma-operator constraint violations: (a,b)=5, &(a,b)
    and (a,b)++ are accepted, and file-scope `int g = (1,2);` is silently
    initialised to 0.

  - %F of infinity prints "inf" rather than "INF"; %E and %G are correct.

  - %f ties at precision 0 round half away from zero, where IEEE and glibc
    round half to even (2.5 -> 3 against glibc's 2).  Consistent across
    %f/%e/%g.  Defensible, recorded so it is not re-reported as a surprise.

  - um80 leaves a stale .rel/.prn from an earlier successful run in place
    when a later assembly fails, so a build script that checks for the file
    rather than the status picks up the old object.

  - um80 accepts a malformed expression: DB 1+*2 assembles to 01.  SILENT.

  - um80 error line numbers inside macro, REPT and IRP expansions point at
    the wrong source line.

  - ul80 reports a multiply-defined global but still exits 0, because L80
    keeps the first definition and produces output.  Whether the status
    should change is a policy question; it would reject link lines L80
    accepts.  uc80's own link line no longer trips it.


Not bugs, recorded so they are not re-reported:
  - Last-digit float differences vs z88dk built with --math-mbf32.  uc80 is
    32-bit IEEE 754; same 24-bit mantissa, different rounding, so results can
    differ by one ULP (5.859874 vs 5.859875).  Working as designed.
  - MKS$/CVS binary round-trips producing garbage.  Those depend on MBASIC's
    float bit patterns, which only MBF gives; not fixable short of adding MBF
    support.  Such programs stay on z88dk.
  - `label: }` rejected - uc80 is right, C17 requires a statement after a
    label.  mbasic was wrong and now emits `label: ;`.
