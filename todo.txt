uc80 - what is left to do
=========================

Fixed work is not recorded here.  CHANGELOG.md carries it, in prose, with
the reasoning; `git log` has the rest.  This file is for what is still
wrong, what has not been tried, and what looks wrong but is not.


Test suites
-----------
The compiler is meant to pass the external suites as far as the target can.
Tests that assumed a particular sizeof(int) / sizeof(long) / sizeof(long
long) are compiled under a switch that matches the assumption (--int,
--long, --long-long), which is what uncovered most of the long-arithmetic
bugs.  Keep going until every test that should run does; the ones that
should not are the few that need more address space than a CP/M TPA has,
like malloc(100000).

uc386, the sister 386 C compiler, was checked on 2026-04-30 and again on
2026-08-20: it references the same four suites we do (c-testsuite, llvm
gcc-c-torture, sdcc-regression, Fujitsu).  Nothing new to import.

Not every suite is checked out on this machine.  ../external holds
c-testsuite and llvm-test-suite; sdcc-regression, compiler-test-suite
(Fujitsu) and z88dk are absent, so run_sdcc.py and run_fujitsu.py cannot
run here at all.  run_fujitsu.py has never had a trial run.

Still open
----------
Each was reproduced against the tree.  "SILENT" marks a wrong answer with no
diagnostic.

Compiler

  - printf field width and the '-', '+' and ' ' flags do nothing on %f, %e,
    %g, %s or %c.  Width is parsed and works for the integer conversions;
    the three flags are matched and discarded for every conversion, so they
    have never been implemented at all.  %10.2f prints "1.50", %10s prints
    "hi".  A feature rather than a fix.  %s and %c are the cheap half -- the
    length is known before the first byte goes out.  %f/%e/%g need the
    handler to capture into a buffer and pad on the way out, which
    _printf_sink already makes possible.

  - Each aggregate-returning call site gets its own slot in the caller's
    frame, and the slots are never reused.  Calls in different statements
    cannot both be live, so they could share; measured over c-testsuite the
    cost is +566 bytes of ??AUTO across 220 programs, so this is an
    optimization rather than a problem.

  - A local past the reach of an (IX+d) displacement is only handled for
    scalar loads and stores, which walk IX to the slot.  The aggregate
    initializer paths -- _gen_local_array_init, _gen_store_member_value,
    _gen_flat_array_init, _gen_array_init_values, _gen_bitfield_init_store,
    _gen_zero_init_member, _gen_string_init, _gen_struct_copy -- still
    format the offset directly, and now raise a CodegenError rather than
    emitting an access that lands somewhere else.  So an *initialized*
    aggregate more than 128 bytes down a stack frame is refused where an
    uninitialized one is fine.  The proper fix is for every one of those
    sites to go through _ix_reach / _ix_release the way the scalar paths do.

  - _merge_array_size compares only the outermost element count.  Inner
    dimensions, element type and declarator shape are never checked, so
    `extern int m[2][3];` followed by `int m[2][7];` is accepted and the
    object's size depends on which declaration came first.  SILENT.

  - A negative or zero array size is accepted -- `int a[-3]` emits `ds -6`
    -- and a floating one is not diagnosed by uc80; it surfaces as a um80
    parse error with no source line.

  - Compound assignment to a 32-bit, 64-bit or float array element
    evaluates the subscript twice, so a side-effecting subscript runs
    twice.  SILENT.  The 16-bit path takes the safe route and the >2-byte
    path falls back to the rewrite that duplicates the target expression.

  - No diagnostic for comma-operator constraint violations: `(a,b)=5`,
    `&(a,b)` and `(a,b)++` are accepted, and file-scope `int g = (1,2);` is
    silently initialised to 0 -- the comma operator is not allowed in a
    constant expression at all (C23 6.6p3).

  - Extended asm and asm goto are not diagnosed when the enclosing function
    is eliminated as dead; the check lives in gen_asm, which never runs for
    code that is not generated.  The AST optimizer also deletes an asm block
    that is unreachable or in a constant-false branch, which matches gcc -O0
    but contradicts the README's "the optimizers do not change, move or
    delete it".

  - `label: }` is rejected: "internal error: unexpected token 'RBRACE'".
    C17 required a statement after a label, but C23 -- which CLAUDE.md names
    as the target -- lifted that (N2508 allows a label at the end of a
    compound statement and before a declaration).  So this is a real gap,
    not the "not a bug" it was filed as, and the message is a parser
    fallthrough either way.  Lives in uc_core's grammar.

  - uc80 --build-libs ignores UC80_LIB_DIR for its destination while
    --print-lib-dir honours it, so `uc80 --build-libs && LIB=$(uc80
    --print-lib-dir)` links against libraries that were never rebuilt.
    SILENT.  build_libs.py reads and writes beside itself and has no
    output-directory option; the cheap half is to refuse the combination
    with a message naming both paths.

Library

  - %lf, %le and %lg are not registered by auto-detection or by
    `--printf float`: _extract_printf_specifiers adds the float feature but
    never the 'long' one, and the table emitter gates the 'l' base entry on
    exactly that.  The conversion is echoed verbatim -- with a warning, so
    not silent -- and mbasic's generated C emits %lg.

  - %.*f and %*f are unsupported: the specification is echoed verbatim, the
    int argument is not consumed, and every later conversion in that call
    reads the wrong argument.  Now diagnosed at compile time wherever the
    format string is a literal; the runtime parser still needs the feature,
    which means reading the vararg whose width is int-size-dependent, so the
    size has to come from the codegen-emitted table the way `int_c` does.

  - pow() is exp(y * log(x)) at binary32 precision, so an exact result is
    not exact: pow(2,10) gives 1023.994812, pow(2,3) 7.999959, pow(10,2)
    99.999938.  An integer-exponent fast path -- repeated multiplication
    when y is a whole number in range -- would fix the common cases.
    sqrt() is exact.

  - Float comparison does not implement NaN's unordered result: `x == x` is
    true for a NaN, and `<` / `>` on one are whatever the magnitude compare
    happens to give.  No arithmetic in rt_float produces a NaN, so this is
    only reachable through the NAN macro or a bit pattern read back as a
    float.  Adding the test costs every float comparison in every program.

  - Float arithmetic has no infinity or NaN handling either: `inf - inf` is
    0.0 and `inf` compares as an ordinary large number.  Same trade.

  - A float division plus the documented link line reports nine duplicate
    globals (__FUNPACK, __FSGN1, __FEXP1, __FMAN1, __FNORM, __FPACK,
    __ITOF, __NEG32, __SEXT32).  The embedded runtime supplies some float
    routines, a libc module references others, the linker pulls
    rt/rt_float.rel to satisfy those, and that module redefines the shared
    cells.  Benign only because L80 keeps the first definition and exits 0.
    The fix has a precedent: give the shared cells their own module, the way
    __sret_buf got one.

  - The CR-suppression state tracks only bytes written through __conout, so
    a console write that bypasses it -- inline asm today, and BDOS-1 input
    echo on real hardware -- leaves it stale and the next '\n' loses its CR.

  - --no-crlf is silently ignored on a translation unit that does not define
    main(), with no warning.  There is precedent for the warning a few lines
    away: a unit that calls printf and defines no main() gets one.

  - %f ties at precision 0 round half away from zero, where IEEE and glibc
    round half to even (2.5 -> 3 against glibc's 2).  Consistent across
    %f/%e/%g.  Defensible, recorded so it is not re-reported as a surprise.

Assembler and linker (../um80_and_friends)

  - ul80 gives every COMMON block the same base address, so two named
    common blocks in one link overlay each other.  Real L80 overlays only
    blocks of the same name.  uc80 no longer depends on this -- separately
    compiled units put their uninitialized data in DSEG -- but hand-written
    assembly using named commons does.

  - ul80 --no-ds-zeros is unsafe for a separately compiled unit: its
    uninitialized data is in DSEG now, and it arrives zeroed only because
    the linker materializes `ds` as zeros.  crt0 zeroes the COMMON region,
    which such a unit no longer uses.

  - um80 assembles an out-of-range (IX+d) displacement, keeping the low
    byte, rather than reporting it.  That is what made the compiler's own
    over-range offsets silent.

  - um80 leaves a stale .rel/.prn from an earlier successful run in place
    when a later assembly fails, so a build script that checks for the file
    rather than the status picks up the old object.

  - um80 accepts a malformed expression: DB 1+*2 assembles to 01.  SILENT.

  - um80 error line numbers inside macro, REPT and IRP expansions point at
    the wrong source line.

  - ul80 reports a multiply-defined global but still exits 0, because L80
    keeps the first definition and produces output.  Whether the status
    should change is a policy question; it would reject link lines L80
    accepts.


Not bugs, recorded so they are not re-reported
----------------------------------------------
  - Last-digit float differences vs z88dk built with --math-mbf32.  uc80 is
    32-bit IEEE 754; same 24-bit mantissa, different rounding, so results can
    differ by one ULP (5.859874 vs 5.859875).  Working as designed.

  - MKS$/CVS binary round-trips producing garbage.  Those depend on MBASIC's
    float bit patterns, which only MBF gives; not fixable short of adding MBF
    support.  Such programs stay on z88dk.

  - Compiling each unit of a program in whole-program mode (the default) and
    linking the results does not work, and is not meant to: each unit embeds
    crt0 and the runtime, so the link fails loudly on duplicate symbols.
    Separate compilation means --no-whole-program, as the README says.
